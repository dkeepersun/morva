# Morva 语言演进决策

本文是 Morva 表达力边界的**约束性决策文档**，回答"这门语言可以长到多大、在哪里必须停"。

它约束后续每一份实现规格：任何扩展语法或语义的规格，必须先在本文的阶梯上声明自己的目标级别，并证明没有越过第 4 节的红线。本文与 [requirements.md](requirements.md) 的关系是——需求基线定义**做什么**，本文定义**能长成什么形状**。

> 状态说明：本文记录的是**已决策的边界**，不是已实现的能力。当前实现停在 L0（见第 3 节）。L1 及以上均**尚未批准实现**，每一级仍需独立规格、验收标准和人工批准。本文不得被引用为"Morva 支持 X"的依据。

---

## 1. 核心判据：精确 ≠ 完整

Morva 的设计讨论反复混淆两个独立的轴，本文先把它们分开：

| 轴 | 含义 | Morva 的立场 |
|---|---|---|
| **精确性** | 无歧义、确定性、可静态检查 | **必须始终为最高**，不可交易 |
| **表达力** | 能表达多大范围的计算 | **有意受限**，本文定义上限 |

一门语言可以极其精确而表达力很小——SQL 约束、正则、Datalog、状态机 DSL 都是。**Morva 属于这一类。**

由此得出两条直接推论：

**推论 A：语法必须严格完整，这一项不参与取舍。**
"描述语言"不意味着语法可以松散。语法一旦有歧义，人与 AI 的理解就会分叉；理解分叉，`.morva` 作为 Source of Truth 的全部价值即告失效。严格语法也是整个系统中最便宜的部分——语义与求解才是成本所在。

**推论 B：Morva 不追求成为编程语言。**
一旦语言图灵完备，Rice 定理生效：任何非平凡的语义性质都不可判定。"这组 requires 有矛盾吗"、"这个状态可达吗"、"这条 ensures 一定成立吗"——全部变为不可回答。而这些问题可被回答，正是 Morva 存在的唯一理由。

## 2. 表达力阶梯

| 级别 | 引入的表达形态 | 可判定性 | 业务规则覆盖（估计） | 决策 |
|---|---|---|---|---|
| **L0** | 字面量、路径、单个比较、子句隐式合取 | ✅ 平凡 | ~30% | **当前位置** |
| **L1** | 析取 `\|\|`、否定 `!`、括号、嵌套谓词 | ✅ SAT（NP-complete，业务规模瞬时） | ~50% | **推荐推进** |
| **L2** | 线性算术、Decimal/负数/String 字面量 | ✅ 线性整数/实数算术可判定 | ~70% | **推荐推进** |
| **L3** | 有限集合、有界量词 `forall`/`exists`、1:N 关系 | ✅ 有界穷举 | ~85% | **冻结**，需真实用例证据 |
| **L4** | 递归、循环、无界迭代 | ❌ **不可判定** | ~95% | **永久禁止进入核心** |
| **L5** | 图灵完备通用编程 | ❌ | 100% | **永久禁止** |

覆盖率是量级估计，用于排序决策，不是可度量的承诺。

### L0 — 当前位置

已实现并有测试覆盖。谓词为单个比较，子句列表构成隐式合取。矛盾检测基于精确字面量事实，保守且不完备。

### L1 — 命题逻辑

引入 `||`、`!`、括号与嵌套谓词后，谓词成为命题公式。**这一级是纯收益区**：

- 表达力显著扩大——"或"在业务规则中密度极高（"VIP **或** 金额超过 500 免运费"），且**当前无任何 workaround**（合取可以靠多条子句，析取不能）；
- 可判定性零损失；
- 静态检查能力**反而增强**——矛盾检测可从字面量启发式升级为对命题部分完备的判定。

### L2 — 线性算术

引入 `+`、`-`、常数系数乘法，以及缺失的字面量种类（Decimal 小数、负数、String）。

线性整数算术（Presburger 算术）与线性实数算术均可判定，混合线性算术亦可判定。业务领域的数值规则——金额合计、数量增减、按比例折扣——绝大多数是线性的。

**本级的红线见第 4.2 节，是本文最重要的单条约束。**

### L3 — 有界量词与集合

"订单至少包含一个商品"、"每个订单项数量必须为正"。有限论域上的量化仍可判定（有界穷举，Alloy 采用的路线）。

**决策：冻结。** 成本是前面所有工作量的总和量级——集合类型、量词语法、模拟器的集合状态、穷举边界策略。仅在真实模型反复撞墙、且有具体案例记录时才可立项。不预先建设。

### L4 / L5 — 悬崖

**L4 是悬崖，不是斜坡。** 跨过之后没有中间状态：静态检查不再能给出可靠答案，模拟不再保证终止，Morva 同时失去"可验证"与"比通用语言更好"两项理由。

## 3. 当前位置与目标位置

```text
L0 ────► L1 ────► L2 ══╣ L3 冻结 ╠══════ L4 ✕ 永久禁止
当前     推荐     推荐      需证据        红线
```

**目标位置：L2。** 长尾覆盖由第 5 节的 `opaque` 逃生舱承担，而不是由继续提升表达力承担。

## 4. 红线

红线是**不可通过普通规格审批跨越**的边界。跨越任何一条都属于重新定义产品，需要按 [requirements.md](requirements.md) 第 8 节的变更控制流程重新协商，并修订本文。

### 4.1 图灵完备红线

核心语言**永远不得**引入：递归定义、循环、无界迭代、无限制的函数抽象，或任何使求值可能不终止的构造。

判据：**`simulate` 必须在与模型规模相关的有限步内终止，且步数上界可静态确定。**

### 4.2 非线性算术红线 ⚠️

进入 L2 时，算术表达式**必须**遵守：

| | 形态 | 判定 |
|---|---|---|
| ✅ 允许 | `a + b`、`a - b`（变量或字面量） | 线性 |
| ✅ 允许 | `a * 3`、`3 * a`（**常数**系数） | 线性 |
| ✅ 允许 | 纯字面量运算（常数折叠） | 平凡 |
| ❌ 禁止 | `a * b`（**变量 × 变量**） | 不可判定 |
| ❌ 禁止 | `a / b`（变量除数） | 不可判定 |
| ❌ 禁止 | `a % b`（变量模数） | 不可判定 |
| ❌ 禁止 | 幂运算、任意非线性函数 | 不可判定 |
| ⏸ 延后 | `a / 3`（**常数**除数） | 可编码，但实现代价高，暂不引入 |

**理由：** 允许变量×变量即进入非线性整数算术。由 Matiyasevich 定理（Hilbert 第十问题），该理论不可判定——不存在能判定任意此类约束是否可满足的算法。这不是"当前求解器不够强"，而是**不存在**这样的求解器。

**这条线必须由 parser 或 checker 显式强制并给出专属诊断码**，不能仅作为文档约定或代码注释。诊断消息应说明这是语言的永久边界，而非未实现的功能——避免使用者反复尝试或等待。

违反此红线的直接后果：矛盾检测的"无误报"承诺（第 6 节）在数学上不再可能兑现。

### 4.3 外部作用红线

模型的静态检查与模拟**永远不得**产生外部可观察作用：不执行实现代码、不访问文件系统/网络/时钟、不读取环境。`implementation_hint` 与 `opaque` 内容**永不**进入求值路径。

## 5. `opaque` 逃生舱

> 状态：**设计决策已定，实现尚未批准。** 语法形状在规格阶段可调整，第 5.2 节的语义约束不可调整。

红线之外的长尾规则（估计约 5%）不通过提升表达力解决，而通过**显式承认无知**解决。

### 5.1 形状

```morva
action ComputeTax(order: Order) {
  requires order.total > 0
  ensures  order.tax >= 0

  opaque "税率按属地规则表计算，不在模型内求解" {
    hint: tax_engine
  }
}
```

### 5.2 不可调整的语义约束

1. **不参与求值。** `opaque` 内容不进入静态证明，也不进入模拟。
2. **必须可见。** `check` 必须报告"该声明含不可分析部分"；`inspect` 必须计数；机器可读输出必须暴露不透明度统计。**任何时候都能回答"这个模型里有多少是黑盒"。**
3. **契约仍受检查。** 包裹 `opaque` 的 `requires`/`ensures`/`invariant` 照常被静态检查——黑盒必须被契约包裹。
4. **模拟必须诚实失败。** 含 `opaque` 的 action 被模拟时，**必须报告为不可模拟**，不得忽略 `opaque` 后继续执行并给出 PASS。虚假的 PASS 比明确的失败危害大得多。
5. **不得成为倾倒场。** `opaque` 用于承载已知无法在模型内求解的规则，不用于绕过尚未实现的表达力。规格评审时，任何"因为 L1/L2 还没做所以先用 opaque"的用法都应被驳回。

### 5.3 与现有兼容容器的关系

`module`、`service`、`event`、`flow`、`lifecycle`、`policy` 当前的行为是：解析通过、内容静默丢弃、`check` 返回 `ok`。**这是本文认定的缺陷**——它与"准确优先"原则（[requirements.md](requirements.md) 第 4 节）直接冲突，且在 AI 生成场景下会把失败伪装成成功。

**决策：兼容容器只能有两种归宿，不存在第三态。**

- 获得真实语义（例如 `lifecycle` 升级为状态机），或
- 归入 `opaque` 语义，按第 5.2 节强制可见。

在其中任一方案落地前，**过渡措施**是让 `check` 对每个兼容容器输出明确的"已解析但无语义"提示。此项独立于 L1/L2，可优先实施。

## 6. 保守近似原则

检查器承诺与不承诺的内容，必须严格区分：

- ✅ **承诺（无误报）：** 报出的每一个矛盾都是真矛盾。
- ❌ **不承诺（允许漏报）：** 不保证所有矛盾都能被报出。未报告**不等于**已证明可满足。

这是 Morva 已在执行的立场（见 [language-reference.md](language-reference.md) 第 4 节），本文将其提升为跨级别的永久原则。

它的实践意义在于**大幅降低 L1/L2 的实现成本**：L2 不需要完备的线性算术求解器，一个区间传播加常数折叠的保守近似即可捕获绝大多数真实错误，且完全不违反已有承诺。求解能力日后可独立增强，语言表面无需变动，也无需为此引入第三方 SMT 依赖。

## 7. 职责分工：描述 what，实现 how

```text
Morva            精确描述 what must be true      可判定、可检查、可模拟
  │
  │  implementation_hint + AI 生成
  ▼
目标语言          精确实现 how                    图灵完备、不可判定（无妨）
  │
  └──────────► 回到 Morva 的 scenario 验证
```

对"精确的具体实现"的需求，由这条通道满足，**不由提升 Morva 自身表达力满足**。不可判定性被隔离在不需要静态证明的一侧。

如果 Morva 自身走向图灵完备，它将既无法证明任何性质，又不及任何一门成熟编程语言——两头落空。

## 8. 准入判据

任何提议扩展语法或语义的规格，必须在其冻结块中回答以下三问，三问全为"是"方可进入实现：

1. **无误报仍可兑现吗？** 引入后，静态检查是否仍能保证"报出的每个错误都是真错误"？
2. **模拟仍可终止吗？** `simulate` 是否仍在有限步内终止，且上界可静态确定？
3. **有真实需求证据吗？** 该形态在实际业务模型中是否频繁出现？需给出具体案例，不接受"以后可能需要"。

L1、L2 三问均为"是"。L3 第 3 问需证据。**L4 第 1、2 问均为"否"——到此为止。**

## 10. 建议实施顺序

顺序建议，非承诺；每一项仍需独立规格与批准。

| 序 | 项目 | 依据 |
|---|---|---|
| 1 | 兼容容器"已解析但无语义"提示 → 演进为 `opaque` | 第 5.3 节；修正正在误导人与 AI 的现有行为，成本最低 |
| 2 | L1 命题逻辑 | 表达力缺口最硬，可判定性零损失 |
| 3 | L2 线性算术与缺失字面量 + 4.2 红线强制 | 覆盖业务数值规则；红线必须与算术同批落地 |
| 4 | 机器可读输出与 AI 接入 | 表达力足够后，AI 生成才不会持续撞墙 |
| 5 | L3 | 冻结，等真实撞墙证据 |
