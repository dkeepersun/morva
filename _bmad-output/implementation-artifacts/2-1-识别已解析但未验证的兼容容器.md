# Story 2.1: 识别已解析但未验证的兼容容器

Status: ready-for-dev

## Story

As a Morva 模型作者,
I want `check` 明确提示只被兼容解析的声明,
so that 我不会把 `module`、`policy` 或其他空壳误认为已被语义验证。

## Acceptance Criteria

1. 给定模型包含 `module`、`service`、`event`、`flow`、`lifecycle` 或 `policy`，当 core 分析模型时，每个兼容容器产生一个稳定、非致命 warning；warning 包含构造类型、名称及声明名称的源码 span。
2. 现有 `check(&Document) -> Vec<Diagnostic>` 与 `Project::check() -> Vec<ProjectDiagnostic>` 继续只返回 error；warning 通过 additive analysis/report API 获取，不能改变 `Diagnostic` 的公开字段或错误调用方的成功判定。
3. `morva check` 对 warning-only 模型在 stderr 安全渲染 `warning[MORVA5001]`、真实路径/行列和 marker，同时在 stdout 保留成功 `ok:`，退出 0。
4. 模型同时包含 warning 与语义 error 时，能够得到两类结果；CLI 以确定顺序呈现并由 error 决定退出 1，不输出成功 `ok:`。Lexer/parser 失败没有 partial AST，因此语法错误只呈现原语法诊断，不扫描源码伪造 warning。
5. 多文件项目中的 warning 映射到责任文件的 `SourceId + LocalSourceSpan`，不得暴露 virtual offset 或误映射到其他文件的相同 offset。
6. 不含兼容容器的模型不新增 warning；既有 core error API、诊断 code/order、CLI 输出及退出码保持兼容。
7. 兼容容器内部被跳过的正文仍不进入强类型语义、checker 或 simulator；warning 只陈述该容器“已解析但未语义验证”，不得暗示内部行为已验证。

## Dev Notes

### Current Implementation Facts

- Parser 已把六种兼容声明解析为 `Declaration::Container(Container { kind, name, declarations, span })`。容器正文的未知项由 `skip_compatibility_item()` 跳过；本 Story 不需要扩大 grammar 或保存原始正文。
- `semantic::check` 当前递归遍历 `declaration.declarations()`，但对 `Declaration::Container` 不做专有检查。类型、action、scenario 的全局短名仍会穿过容器收集；warning 不能改变这些既有规则。
- `Diagnostic` 只有 `code/message/span`，其 `Display` 固定为 `error[...]`。不要给它增加 severity 字段；这会破坏公开 struct literal、相等性和现有调用方。
- `Project::document()` 使用 virtual spans；`Project::check()` 已通过 `SourceMap::locate_virtual_span` 恢复 `ProjectDiagnostic::Source`。新 warning 必须沿用这个边界。
- CLI 的 `load_checked_model()` 当前在返回模型前执行 error-only check。实现 warning+error 同时呈现时，应抽取共享加载/分析步骤，而不是重复单文件/目录 IO 管线。
- CLI 的 `render_diagnostics()` 已提供安全路径、通用换行、escaped-width 160 窗口和 caret 对齐。warning renderer 应复用同一 `SourceView` 数据，而非复制算法。

### Required Additive API Shape

- 推荐独立 `analysis.rs`，定义 `NoticeKind::CompatibilityContainer { kind, name }`、`Notice`、`AnalysisReport`（或等价清晰名称）并从 `lib.rs` re-export；warning code 使用 `MORVA5001`，severity 由 notice/finding 类型表达。
- Report 至少能分别访问 errors 与 warnings，并提供稳定的合并视图。`analyze(document)` 调用现有 semantic check 获取 errors；`check(document)` 保持原路径和顺序，不能改为对 source-sorted report 做过滤。
- Project 层需要对应的 source-aware report/notice 包装；不得把 warning 塞进 `ProjectDiagnostic` 后再靠 message 判断 severity。
- 新 API 必须是纯 core、标准库实现，不引入第三方依赖、文件系统或 CLI 类型。

### Ordering and Rendering Contract

- Warning 的责任 span 固定为容器 `name.span`，避免整块 marker 过大，并稳定标识构造。
- 六种兼容 kind 均使用同一 `MORVA5001`，kind/name 在结构化 notice category 和固定 message 中区分；不要为每个 kind 分配不同 code。
- Warning 按源码 span 排序；多文件先按装配 source order，再按 local span。warning 与 error 同位置时使用显式、测试锁定的 tie-break。
- `check()` 的现有 error vector 必须保持原顺序。只有新增 analysis/CLI 合并视图可应用跨 severity 排序。
- CLI 首行必须明确显示 `warning[MORVA2024]`，不能复用 `Diagnostic::Display` 后仍写成 `error[...]`。

### Example Compatibility Caveat

- `examples/order.morva` 含 `module Orders`，因此 Story 完成后 `morva check examples/order.morva` **预期新增一个 warning**；这是一项已批准的可见性改进，不得伪造“check 文本不变”。
- `examples/order-project` 没有 compatibility container，但含 soft behavior；Story 2.2 尚未实现，因此本 Story 后它不应产生 warning。
- 两套示例的语义、parse/inspect 内容、七阶段模拟、最终状态和退出码必须保持不变。无容器 fixture 用于证明真正的 no-warning 输出兼容。

### Scope Boundaries

- 不处理 `atomic`、`idempotent`、`timeout`、`retry`、`implementation_hint` warning；它们属于 Story 2.2。
- 不给 inspect 增加未建模摘要；属于 Story 2.3。
- 不实现 capability inventory/`morva capabilities`；属于 Story 2.4。
- 不修改 parser 兼容白名单、容器作用域、AST 公共形状、simulation、Boolean 表达式、JSON 或 MCP。
- 不实现 parser recovery、partial AST 或基于原始文本扫描的 warning；lexer/parser 失败继续只返回原有语法诊断。
- 不回显被跳过的兼容正文，不把 warning 升级为 error，不因 warning 改变 exit code。

### Testing Requirements

- 所有新断言尽量锁定 exact code、message、span、severity、顺序、stdout/stderr 和退出码，不只断言“存在 warning”。
- 使用公开 `analyze`/Project seam 和真实 CLI process seam；不得只测私有 helper。
- 对 mixed warning+error 必须证明 analysis 没有因 error 提前返回，同时旧 `check()` 保持 error-only。
- 对 clean model 必须精确证明没有 warning；对 `order.morva` 必须精确证明一个 container warning 且仍成功。
- 门禁使用 `--locked`；示例命令串行运行，避免 CLI 临时夹具并发争用。

### Library / Framework Requirements

- 本 Story 不需要外部技术或最新第三方 API 调研。
- `morva-core` 继续只使用 Rust 标准库；禁止为 severity、排序或报告模型引入 serde、logging、CLI 或 async 依赖。
