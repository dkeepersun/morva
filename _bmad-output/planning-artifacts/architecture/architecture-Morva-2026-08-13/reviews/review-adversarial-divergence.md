# Adversarial Divergence Review

## Verdict

**NEEDS CHANGES.** The spine successfully fixes the authority boundary, invalid-result gate, local provenance unit, coverage/validity distinction, and human-only acceptance. It does not yet fix enough of the public semantic algebra or workflow state machine for two downstream units to interoperate. The pairs below can obey every adopted AD literally and still disagree about the meaning, consumability, or reviewability of the same revision. The explicit deferral of the full checked-model projection makes this a design draft, not yet a stable v1 implementation substrate.

## Adversarial construction

Assume two independent, conforming units:

- **Atlas** is a Rust CLI/AI adapter that accepts only semantic variants it understands, represents child concepts with explicit records, canonicalizes project inputs before hashing, and reviews every candidate against the accepted head.
- **Boreal** is an editor/review adapter that preserves or skips unknown semantic variants, represents child concepts as declaration-specific extension objects, retains caller-provided project order, and reviews a revision against the immediately preceding candidate.

Both delegate all semantic facts and invariant validation to `morva-core`; emit no checked model on errors; use exact inline UTF-8 bytes and local half-open ranges; treat IDs as document-local; keep coverage separate from validity; require an explicit human decision; avoid Rust layout leakage; reject unknown protocol majors; emit deterministically; remain local; use the stated SHA-256 framing; present the evidence named by AD-12; and call the core invariant validator. None of those commitments forces the choices on which Atlas and Boreal differ below.

## Findings

### 1. [P1] v1 has no interoperable checked-semantic algebra

- **Incompatible pair:** For an entity field, Atlas emits `{ "name": "status", "type": { "kind": "enum", "semantic_key": "enum:OrderStatus" }, "location": ... }`. Boreal emits `{ "kind": "field", "name": "status", "declared_type": { "kind": "enum", "semantic_key": "enum:OrderStatus" }, "location": ..., "semantic_key": "field:Order.status" }`. Both are core-owned projections of named language concepts, contain normalized resolved references, exact provenance, and no Rust internals, so both satisfy AD-1, AD-3, and AD-7. The schema accepts both because `fields`, `members`, `parameters`, `clauses`, and `items` are arrays of unconstrained objects. A consumer written for either shape cannot consume the other.
- **Further divergence:** Required members per declaration kind are unspecified. An `action` with no `parameters` member can mean “zero parameters” to Atlas and “parameters were not projected” to Boreal. The same ambiguity exists for absent versus empty fields, enum members, clauses, scenario items, expression variants, and assignment targets. `additionalProperties: true` cannot solve absence semantics.
- **Impact:** `morva.checked-model.v1` advertises a capability that does not denote a stable machine contract. A schema-valid document can carry mutually unreadable checked models while claiming the same protocol major and capabilities. AI comparison can also mistake omitted projection data for an empty semantic set.
- **Required closure:** Before calling the protocol v1, define a closed, discriminated algebra for every currently emitted declaration, field/member/parameter, clause, assignment, scenario item, expression, and type-reference shape. For each variant specify required versus optional members, absence semantics, ordering, normalized builtin names, ownership/nesting, and exact referential constraints. If that work remains deferred, remove `morva.checked-model.v1` from the mandatory v1 contract and scope v1 to sources/findings/coverage only.

### 2. [P1] Unknown semantic variants and language versions have no single fail/continue rule

- **Incompatible pair:** Given protocol v1 with `language_version: "0.2"` and a new declaration or expression discriminant, Atlas rejects the complete checked model. Boreal preserves the unknown object, skips it during its analysis, and continues over known nodes. Both reject unknown protocol majors, ignore unknown object members, do not map the unknown discriminant to a known operation, and inspect the same mandatory capability strings, satisfying AD-8 literally. Neither AD-8 nor the companion protocol says whether an unknown discriminant invalidates the subtree, the checked model, or the entire document. It also never states whether an unsupported `language_version` is rejectable.
- **Impact:** Atlas reports “unsupported document” while Boreal may report a successful partial review of a producer-declared `fully_modeled: true` document. `coverage` describes producer coverage, not consumer comprehension, so Boreal has no required way to expose that its semantic view is incomplete. This is a silent semantic split under one major version.
- **Required closure:** Specify fail-closed granularity for every semantic discriminant and for unsupported language versions. A robust v1 rule is: every additive semantic variant requires a capability; a consumer that lacks any capability required by content MUST reject semantic use of the entire checked model, while it MAY still display sources/findings. Separate producer coverage from consumer comprehension and define a machine-visible unsupported result. Clarify whether new discriminants are actually compatible within v1; the current compatibility paragraph and AD-8 do not decide that.

### 3. [P1] Review evidence has no authoritative lineage or acceptance precondition

- **Incompatible pair:** Starting from accepted revision `R0`, AI produces invalid `R1`, revised-but-drifting `R2`, then valid `R3`. Atlas binds the review to current accepted head `R0` and requires the candidate to name `R0` as its base. Boreal treats `R2` as the “base revision” allowed by AD-12 and presents the `R2 → R3` checks. Both include original intent, a base or accepted revision, the complete revised candidate, findings/coverage “from both checks,” and diagnosis/rationale; both require a human click before acceptance. Yet Boreal can hide drift introduced in `R1/R2`, while Atlas exposes the cumulative `R0 → R3` change.
- **Second divergence:** Atlas forbids `accept` when `coverage.fully_modeled == false`. Boreal permits an informed human to accept after acknowledging every unmodeled entry. AD-5 forbids interpreting validity as completeness and AD-6 makes acceptance human-only, but neither defines the legal transition. Both workflows comply and can assign different Source-of-Truth states to the same evidence.
- **Impact:** The human gate is not a reproducible state machine and does not prevent stale-base acceptance, lost updates, or cumulative semantic drift. “Both checks” is ambiguous after more than one revision, and `accepted or base` allows an unaccepted AI candidate to become the comparison anchor.
- **Required closure:** Define a revision graph and immutable review-envelope identity. At minimum require `accepted_revision`, `candidate_revision`, `candidate_parent_revision`, original intent identity/version, and all intermediate check/diagnosis events or an explicit cumulative diff from accepted head. Acceptance MUST use compare-and-swap against the still-current accepted revision. Decide and encode whether incomplete producer coverage forces `block`, or define the explicit approved opaque-boundary evidence that permits acceptance.

### 4. [P1] Multi-file ordering and logical-name identity are not owned at the core boundary

- **Incompatible pair:** Atlas sorts project sources by exact UTF-8 logical-name bytes before projection and project hashing. Boreal preserves the caller-supplied order because the protocol says sources retain CLI discovery order and AD-9 refers to “source order semantics.” Both use exact source bytes and the AD-11 length-framed SHA-256 stream, and each deterministically emits the order it considers authoritative. The spine permits CLI/adapters to discover inputs while `morva-core` owns projection, but does not say which layer owns canonical project ordering or whether the core must reject a non-canonical caller order.
- **Name divergence:** For a filesystem name represented in decomposed Unicode, Atlas retains exact UTF-8 bytes; Boreal normalizes the logical display name to NFC before creating `source_id` and framing the project digest. AD-3 makes source *content* exact but says nothing equivalent for logical-name bytes. Both can plausibly claim `source:<logical-name>` and an exact length-framed project stream.
- **Impact:** Identical source files can acquire different `subject.revision`, source order, source IDs, finding ordinals, node IDs, and serialized bytes. Review lineage and cache keys then diverge even though every semantic fact is core-derived. This undermines AD-9 and makes AD-11 non-interoperable outside one CLI code path.
- **Required closure:** Move ordered project-source assembly into one normative core input type, or define and validate canonical order independently of caller order. Define “logical name” as exact UTF-8 bytes obtained by a stated discovery algorithm, forbid Unicode normalization/percent-encoding unless specified, define duplicate/collision handling, and bind source-ID construction plus project digest framing to that representation. Add conformance vectors for empty content, multi-byte names, canonically equivalent Unicode names, colons/control characters, and reordered inputs.

### 5. [P2] The core/CLI error boundary has no machine-readable ownership rule

- **Incompatible pair:** On an unreadable source or a source that changes during discovery, Atlas emits no protocol document and returns a CLI transport/input failure. Boreal emits a separate machine JSON error envelope and no checked-semantics document. A third implementation may attempt to synthesize a `category: project` finding even though the core never received exact bytes. All can preserve AD-1 by declining to call synthesized data checked semantics, and AD-2 only constrains a `result` once such a result exists.
- **Impact:** A machine consumer cannot distinguish “Morva invalid” from “no authoritative check happened” without CLI-specific stderr/exit-code knowledge. Attempting to force the event into the current schema conflicts with mandatory inline content and exact primary locations. This is an ownership seam between the CLI discovery allowed by AD-1 and the core-owned protocol.
- **Required closure:** Specify the emission contract for pre-core failures: either no protocol bytes plus a normative exit-status taxonomy, or a distinct versioned operation/error envelope that cannot be mistaken for checked semantics. Explicitly prohibit adapters from synthesizing Morva findings for unreadable or unstable inputs.

## Non-holes confirmed

- Document-local `node_id` and `finding_id` algorithms may differ without harm if consumers truly treat them as opaque references inside one document; the problem begins only where the draft uses unconstrained `semantic_key` values as resolved references.
- Exact inline source bytes intentionally rule out a redacted document claiming the mandatory v1 source capability. AD-10 correctly prevents remote upload in the first increment. A future remote/redacted capability needs a separate threat model, but its deferral does not make the local v1 boundary internally contradictory.
- JSON property ordering and escaping can vary across independent producers without changing JSON meaning. AD-9 promises byte reproducibility for identical inputs, producer, and options, not a cross-producer canonical-JSON standard. Extension-member order should be specified only if cross-implementation byte identity becomes a requirement.

## Gate condition

Do not implement or advertise `morva.checked-model.v1` until findings 1–4 are resolved in the spine and protocol, encoded where possible in the schema/core validator, and exercised with cross-implementation conformance vectors. Finding 5 may be closed in the implementation specification, but it must be decided before exposing the CLI as a reliable machine surface.
