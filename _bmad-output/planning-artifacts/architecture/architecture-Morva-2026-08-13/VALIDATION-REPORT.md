# Morva AI Loop Validation Report

> Date: 2026-08-13
> Scope: information model and human-gated state flow, not production protocol implementation
> AI provenance: sample requirements and candidates were generated by an independent Codex agent; current Morva CLI supplied all observed diagnostics and exit codes.

## Verdict

**The protocol shape is sufficient for the tested loop, provided human review remains an independent state outside protocol validity.**

The samples established three different outcomes:

| Sample | First check | Revision check | Human outcome | What it proves |
|---|---:|---:|---|---|
| A — enum typo | exit 1, `MORVA2012` | exit 0 | accept | Exact finding provenance supports a semantics-preserving repair |
| B — unsupported OR/NOT | exit 1, `MORVA1018` | exit 0 | reject/block original | A valid checked model does not prove preservation of natural-language intent |
| C — warning-only soft behavior | exit 0, three warnings | exit 0 | block | Exit success and even zero warnings after revision do not prove omitted operational requirements |

This falsifies the unsafe state model `check success → accepted`. The required model is `check result → AI explanation/revision → fresh check → human decision`.

## Method

1. An independent AI agent read the current language reference and example.
2. It generated three natural-language requirements and complete first-pass `.morva` candidates.
3. Each candidate was saved without correction and checked by:

   ```sh
   cargo run -q -p morva-cli -- check <sample>
   ```

4. The AI diagnosed the expected issue and generated a complete replacement candidate.
5. Each replacement was checked in a new CLI invocation.
6. Human-review decisions were evaluated against the original requirement, both candidates, all findings, and the AI rationale—not against exit code alone.
7. All six protocol snapshots embedded by the executable prototype were validated for shape against the draft JSON Schema with `check-jsonschema`.

The sample sources are in [samples](samples/). The interactive state machine is [morva-ai-loop.prototype.html](../../../../docs/prototypes/morva-ai-loop.prototype.html).

## Sample A — diagnostic-preserving correction

### Requirement

Only an order in `Paid` may be fulfilled; afterward its status must be `Fulfilled`.

### Generated candidate

[a-generated-invalid.morva](samples/a-generated-invalid.morva) writes `Fulfiled` in the effect.

Observed result:

```text
exit 1
error[MORVA2012]: unknown member 'Fulfiled' for enum 'OrderStatus'
  --> .../a-generated-invalid.morva:16:28
 16 |     effects order.status = Fulfiled
    |                            ^^^^^^^^
```

Protocol consequence:

- `result.status = invalid`;
- one error finding with source-local byte range `[247, 255)`;
- `checked_model = null`;
- coverage assessment can still be `complete` because parsing and additive analysis completed.

### Revision

[a-revised-valid.morva](samples/a-revised-valid.morva) changes only `Fulfiled` to `Fulfilled`.

Observed result:

```text
exit 0
ok: .../a-revised-valid.morva
```

### Human decision

**Accept.** The revision follows the exact finding and preserves every stated precondition, effect, and postcondition.

## Sample B — a green result with semantic drift

### Requirement

The same `Resubmit` action is allowed when status is `Pending` **or** `Failed`, provided the request is not suspended.

### Generated candidate

[b-generated-unsupported.morva](samples/b-generated-unsupported.morva) uses `or` and `not`, which are outside Morva L0.

Observed result:

```text
exit 1
error[MORVA1018]: unexpected token after clause expression
  --> .../b-generated-unsupported.morva:15:40
 15 |     requires request.status == Pending or request.status == Failed
    |                                        ^^
```

Protocol consequence:

- `result.status = invalid`;
- syntax finding at byte range `[256, 258)`;
- `checked_model = null`;
- `coverage.assessment = unavailable`, because parsing stopped before a complete coverage scan.

### Revision

[b-revised-semantic-drift.morva](samples/b-revised-semantic-drift.morva) replaces `not suspended` with an equivalent Boolean comparison but silently drops the `Failed` branch.

Observed result:

```text
exit 0
ok: .../b-revised-semantic-drift.morva
```

### Human decision

**Reject the revision and block the original requirement.** The revision is valid Morva but implements only `Pending AND not suspended`. It cannot satisfy the original disjunction. A language extension, an explicitly approved decomposition, or a requirement change is needed.

This is the decisive validation case: a checked semantic representation proves facts about the candidate, not equivalence with an unstructured requirement.

## Sample C — warning-only semantic coverage

### Requirement

Refund approval must be atomic and retry transient failure at most three times, in addition to the `Pending → Approved` transition.

### Generated candidate

[c-generated-warning-only.morva](samples/c-generated-warning-only.morva) uses a compatibility `module` plus `atomic` and `retry 3` soft behavior.

Observed result:

```text
exit 0
warning[MORVA5001]: compatibility module 'Refunds' is parsed but not semantically validated
warning[MORVA5002]: action 'ApproveRefund' soft behavior 'atomic' is parsed but not semantically validated or executed by simulation
warning[MORVA5002]: action 'ApproveRefund' soft behavior 'retry' is parsed but not semantically validated or executed by simulation
ok: .../c-generated-warning-only.morva
```

Protocol consequence:

- `result.status = valid` because there is no error;
- three warning findings;
- `coverage.assessment = complete` and `coverage.fully_modeled = false`;
- `checked_model` may contain the verified status transition, but `atomic` and `retry` stay outside it.

### Revision

[c-revised-still-blocked.morva](samples/c-revised-still-blocked.morva) removes compatibility/soft syntax and leaves an explicit review-blocker comment.

Observed result:

```text
exit 0
ok: .../c-revised-still-blocked.morva
```

### Human decision

**Block.** The revised state transition is valid, but a comment neither models nor proves atomicity or the retry bound. Removing warnings cannot erase a mandatory source requirement.

## Protocol-schema shape validation

The schema itself passed its Draft 2020-12 metaschema check. The prototype then materialized six complete protocol snapshots. The revised Sample A snapshot contains a non-empty checked model with enum, entity, action, parameter, three clause forms, paths, enum-member values, one assignment, and binary expressions:

- A generated and revised;
- B generated and revised;
- C generated and revised.

Every snapshot passed `check-jsonschema` against `morva-checked-semantics-v1.schema.json`. The executable extraction also confirmed that all six inline `sources[].content` values match the corresponding evidence files byte-for-byte.

Eight schema-level negative mutations were also rejected as required:

- missing mandatory `morva.coverage.v1` capability;
- `valid` result containing an error finding;
- `invalid` result containing no error finding;
- `valid` result with unavailable coverage;
- known `action_soft_behavior` detail missing its owning action.
- unknown declaration discriminant;
- action declaration missing required `clauses`;
- unsupported `language_version`.

A source-less empty-project envelope with `sources: []`, subject-scoped `MORVA2023`, unavailable coverage, and no checked model also passed shape validation. Known-answer SHA-256 vectors were generated for an empty file, an empty project, and a two-file project containing a multibyte UTF-8 name plus CRLF content; the values are fixed in the protocol draft.

Two compatibility/provenance shapes also passed: an unknown extra object member was ignored, while a project checked system carried two ordered `shell_locations`. This complements the negative proof that unknown semantic discriminants fail closed.

This proves shape conformance only. JSON Schema cannot enforce cross-record source references, byte-range bounds against string bytes, or one-to-one warning/coverage correspondence. The architecture therefore requires a separate `morva-core` semantic-envelope validator before any production document can claim protocol conformance. That validator is designed here but not implemented or validated in this task.

## Validated decisions

1. Invalid results must carry `checked_model: null`.
2. Coverage needs an explicit `complete | unavailable` assessment; a Boolean alone cannot represent early parse failure.
3. `valid` and `fully_modeled` are independent.
4. Human review is a separate workflow decision, not a protocol result state.
5. Revisions must be complete new candidates and must be checked from scratch.
6. Review input must retain original requirement, both source revisions, findings/coverage, and AI rationale.
7. Exact source-local byte ranges are sufficient for the tested diagnosis and traceability flow.
8. Human review requires the original intent, base and revised sources, relevant findings/coverage, and AI rationale as one evidence bundle.
9. Candidate lineage remains anchored to the current accepted revision and frozen intent identity/version; the prototype rejects acceptance unless the fresh result is `valid` and all three compare-and-swap bases still match.
10. Unknown semantic discriminants and unsupported language versions fail closed, while unknown object metadata remains additive.

## What was not validated

- Full executable projection of every current AST/expression/scenario variant; the schema now closes their shapes, while the prototype materially exercises the action slice only.
- The core-owned semantic-envelope validator and its negative/property tests.
- A production multi-file digest implementation and virtual-to-local span projection; only design vectors and system-shell shape are validated here. SHA-256 adoption remains an explicit `[ASSUMPTION]` and pre-production change-control gate.
- Large-project output size, streaming, redaction, remote model transport, or editor coordinates.
- Whether SHA-256 should enter the zero-dependency implementation; this remains `[ASSUMPTION]` pending change-control review.
- AI quality beyond these three deliberately selected boundary cases.

## Recommendation

Proceed only to an implementation specification for a read-only core projection plus a separate CLI emission surface. Keep AI orchestration, automatic source mutation, MCP, incremental caching, and remote transport out of that first increment.
